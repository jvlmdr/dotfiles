# Decisions

Directives the author identified while developing this skill, in their words, for maintainers.
SKILL.md deliberately does not link here, so agents running the skill do not load it.

- **Natural tests, written the way a person would.**
  "I want (correct) natural tests that humans would write" (opening a test cleanup); "Are all of these tests that a human would likely right? Nothing unnatural?" (after the agent listed new test files, offering to fold two into existing ones); "Tests all good? Natural? Humanlike?" (after the agent applied comments to a reader change and asked to commit); "How can I add natural tests just to make sure that my stuff has no errors?" (on example scripts, after "I don't want to make too many changes").
- **Not too clever; the thing under test stays visible.**
  "I think one principle might be: Tests shouldn't be too 'clever'. The way in which they use the object being tested should be clear. For example, I don't like how [the wait helper] takes [the object under test]" (on a wait helper taking the object under test, after the agent listed cleanup steps); "I like the thing being tested to be visible in the test, not wrapped up, and nothing too clever" (asking the agent to pass it to the running Sonnet audit); "I actually agree that with contextlib.closing() is less obscure than hiding behind [a factory helper]" (agreeing with the Sonnet auditor against the agent's "Disagree" on a factory helper).
  On review: "Maybe I'm being too strict on this one?" (2026-10-05, on a draft rule against any helper that uses the system under test; the rule became "or does more than its name says").
- **Through the public interface; don't break the abstraction.**
  "Do many of our tests probe internal hidden elements? Is this possible to avoid?" (while reviewing two PRs); "Is this a general principle? Tests should not access private members and should not break the abstraction" (on a test that mocked a dependency; the agent's inventory had missed it); "I mean, why do the tests access internal [stuff]??" (after the agent argued to keep a helper isolating a private method call); "use the public interface to determine appropriate tests and watch for excessive mocking or monkeypatching" (in a /final-review request, after asking whether a forward method was useful); "...Or they might reach into the internals just so that our current change has a test" (proposing the test taxonomy).
- **Mock and monkeypatch sparingly.**
  "Just make sure that we're not overly testing, or fixing behavior yet to be decided, or monkeypatching tests into oblivion" (after an agent proposed tests for a resource-release design not yet agreed).
- **When something is hard to test, question the design; change it only for its callers.**
  "Have we designed it badly? Being difficult to test usually means that" (after the agent offered a 0.2 s sleep window or dropping the "close() waits" claim); "I don't see how we can honestly test this" (replying to a proposal to remove an assertion that closing had not finished; the test was dropped); "Actually no. I agree, reshaping production code just to test" (rejecting a Protocol added only for testing, after first agreeing to it).
- **Don't settle undecided behavior.**
  "I'm tempted not to add or modify tests that over-specify behavior which we haven't decided yet" (after the agent asked about edge-case inputs to an internal API); "*Don't* add a test that bool is supported though!" (after the agent let bools through as ints and commented it); "...just to assert a particular behavior that we changed but wasn't settled" (proposing the test taxonomy); "Just make sure that we're not overly testing, or fixing behavior yet to be decided, or monkeypatching tests into oblivion" (after an agent proposed tests for a resource-release design not yet agreed).
- **Tests must earn their place.**
  "They might exist just to ensure coverage..." (proposing the test taxonomy); "I'm not sure if we need a test for this?"; "I'm not sure if *any* of [the server-launch tests] should exist"; "That seems excessive" (after the agent explained a test for a missing optional estimate), but not as a rule against such tests: "I don't think we necessarily need to prevent tests for inputs that don't occur in the current state (someone might do it in the future)." (after the agent split the draft principle's "inputs nothing produces" clause from undecided behavior); "No need to test the report generation"; "Also look for any tests that are excessive e.g. testing simple report generation"; "These are examples. I don't think they should have tests"; "We don't want to have vacuous tests for example files, but it would be good to know if it is out of date, has typos, or uses things that don't exist", then "maybe pyright is better for this?" (asking for a balanced CI review after a push, then on an import-test proposal).
- **One behavior per test.**
  "Unit tests shouldn't put too many things together?", then "Agreed" to one behavior per test with exceptions for end-to-end runs and sequences whose order is the behavior; "Let's leave the bare version for now. One thing per test" (declining the agent's parity coverage between two code paths via a refactor).
- **No message-text or stderr assertions; avoid subprocess tests.**
  "Actually, I don't like text assertions unless it really makes sense"; "I think the assertions about stderr are ugly?"; "I think we shouldn't test stderr at all?"; "In general, that test seems ugly to me (uses subprocess, checks for text in help)"; "I don't like the subprocess thing still?"; "I'm particularly sensitive to subproc tests and text-matching tests" (in the message launching the Sonnet audit).
- **Fixtures for setup that is expensive or needs cleanup, not as a general fixture that hides how the code is used.**
  "This [shared] fixture is a bit suss. It doesn't test things as they are used"; "I just want the code to read more naturally. I find the current [shared] fixture extremely opaque"; "I think we should think about what we actually want to achieve with the fixture" (after the agent offered per-object entries versus a factory fixture); "Fixtures should mainly be used for expensive setup. Otherwise we can just have a shared util function"; "And IIRC, we made this a fixture for cleanup purposes?", then "We should document why things are a fixture" (on a fixture kept for cleanup).
  On review: "Maybe the larger objections was to a 'god object'-like fixture which made the use of the code being tested unclear" (2026-10-05).
  "It just felt very far from typical usage, and required the reader to learn a new concept just to read the tests" (2026-10-08, on why the shared fixture was wrong; the General Fixture line now states that cost rather than the fixture's form).
- **A test's verdict must not depend on timing; timeouts only for failure.**
  "I see.. putting sleeps in tests is not good, right?"; "I'd rather not have polling here btw" (on a proposed predicate-polling release helper); "Is it dangerous to have timeouts in tests?" (in a batch of proposed edits; the agent answered deadlines are safe).
  On review: "I think we can have some kind of exception to this which exists in the codebase. Timeouts only for failure? That is, if all tests pass, it runs without timeouts?" (2026-10-05).
- **Stored test data: small and stable, or the artifact under test.**
  "What is the fixture size? Are we storing a large data blob in the repo?"; "I'd rather avoid blobs..." (after the agent gave size options for a binary fixture).
  On review: "It's kind of acceptable to have like 1 image or something that is unlikely to ever change? Not long videos or large images?" (2026-10-05).
